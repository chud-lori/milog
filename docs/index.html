The monitor for the box you run yourself.

One bash file watches your logs, your host, your file integrity and your kernel, then tells you on Discord when something changes. No agent fleet, no collector, no retention tier.

Written for people who run one server, or three, and read the logs themselves. This page is also the command reference.

v0.6.0 MIT, single file bash 4+, Linux apt / dnf / yum / pacman / apk

curl -fsSL https://raw.githubusercontent.com/chud-lori/milog/main/install.sh | sudo bash

Prefer to read it first? install.sh is plain bash. It runs on Linux only and exits on any other OS before installing anything.

SURFACES

Six things it watches, one alert pipeline

Everything below fires through one alert pipeline, with the same per-rule cooldown, silences, routing and hooks. Request-log rules also share a dedup keyed on (ip, path), so a line that matches two rules alerts once. Turning on a new surface does not mean a new place to configure alerts.

Request logs nginx, journald, docker, text

nginx combined format gets the full treatment. Other sources are tailed, grepped and searched, and skip the parsing modes.

  • Per-app req/min, 2xx through 5xx, p50 / p95 / p99
  • Top paths, top source IPs, slowest endpoints
  • Anomaly against the same minute over the last 14 days

Host vitals /proc

Read straight from the kernel, so nothing extra has to be installed.

  • CPU, memory, disk, worker count against your thresholds
  • No sar, no iostat, no collector

Attack payloads heuristic

Pattern matching over request lines, tuned for what actually hits a small box.

  • LFI, RCE, SQLi and XSS shapes in URLs
  • Infra probes: .git, .env, wp-admin, phpMyAdmin
  • CMS scans and dotfile probes

Scanners user-agent catalog

Ranked by behaviour, not just by name, so a renamed agent still surfaces.

  • zgrab, masscan, nikto, sqlmap
  • Shodan, CensysInspect, bare HTTP libraries
  • AI crawlers: GPTBot, ClaudeBot, CCBot

Host integrity milog audit, any host

Baseline once while the box is known good, then diff. Needs no web server at all, so it works on a host that serves nothing.

  • FIM over passwd, shadow, sudoers, crontab, sshd_config, authorized_keys
  • Persistence: cron dirs, systemd services and timers, rc.local, ld.so.preload
  • Listening ports, passwd and sudoers, SSH keys
  • YARA over the webroot, rootkit heuristics

Kernel events eBPF sidecar, Linux

An optional Go binary. Catches the short-lived process that a log tail never sees.

  • exec: a shell under a web worker, a binary run from /tmp
  • tcp connects to destinations outside the allowlisted CIDRs
  • file opens of shadow, sudoers and SSH config by processes outside the allowlist
  • ptrace, kmod, bpf-load
  • Retransmits and syscall rate, Welford sigma

CONFIG

Point it at your logs

A bare name means an nginx access log in LOG_DIR. A prefix means something else, which is how MiLog watches an app that never touches nginx. 

# ~/.config/milog/config.sh
LOGS=(
  api                                  # $LOG_DIR/api.access.log
  nginx:storefront                     # the same thing, said explicitly
  text:worker:/var/log/worker/out.log  # any text file
  journal:mybot.service                # streams via journalctl
  docker:postgres-prod                 # the container's stdout
)
What each source type supports
SourceResolves toSupports
api$LOG_DIR/api.access.logeverything
nginx:apithe same file, explicitlyeverything
text:name:/paththat filetail, grep, search, errors, patterns
journal:unitjournalctl -u unit -ftail, grep, search, errors, patterns
docker:namethe container JSON logtail, grep, search, errors, patterns

The counting modes need the nginx combined format to read a status code and a latency, so they stay with nginx sources. Host integrity audits and the kernel probe read no logs at all and work on any host.

Getting it running

Step 1 is the whole install. The rest are the things worth turning on afterwards, in the order they pay off.

  1. Install

    curl -fsSL https://raw.githubusercontent.com/chud-lori/milog/main/install.sh | sudo bash

    Linux only. Drops milog into /usr/local/bin, pulls gawk, curl and sqlite3 through apt, dnf, yum, pacman or apk, and stops with an error on a host with none of those. The milog-web, milog-tui and milog-probe binaries come from the latest release, and each archive is checked against that release's checksums.txt (SHA-256); a mismatch aborts the install. checksums.txt is not signed, so this catches a corrupted or swapped download, not a compromised release. milog.sh itself is fetched from the main branch and is not checksummed.

    The release page also has .deb, .rpm and .apk packages for amd64 and arm64.

  2. Look at it

    milog doctor     # what is missing before anything else
milog monitor    # the dashboard

    Run doctor first. It checks the log format, which is the one thing that quietly halves what MiLog can tell you.

  3. Get told about it

    sudo milog alert on 'https://discord.com/api/webhooks/ID/TOKEN'
milog alert test

    alert on writes the Discord webhook to your config and installs milog.service, which runs as the user who ran sudo. alert test sends one message to every configured destination. Slack, Telegram, Matrix and a generic webhook are set with milog config set, described in docs/alerts.md; alert on still wants a Discord webhook before it installs the service.

  4. Baseline the host while it is still clean

    milog audit fim baseline
milog audit ports baseline
milog audit accounts baseline

    Drift detection compares against a known-good snapshot, so a baseline taken after a compromise records the compromise as normal. This is the step worth doing today rather than eventually.

  5. Bank history, then let it judge

    milog config set HISTORY_ENABLED 1
sudo systemctl restart milog.service
# two weeks later
milog config set ANOMALY_ENABLED 1
milog auto-tune 7

    The anomaly detector compares each minute against the same minute over the previous days, so it needs days before it says anything. It stays quiet until it has them.

  6. Kernel events optional, Linux

    sudo milog probe install-service
sudo journalctl -u milog-probe.service -f

    Catches what a log tail structurally cannot: the process that started and exited between two reads. Same webhooks, same cooldown. The unit runs the probe as root, limited by a systemd capability bounding set, and the alerts it raises run as the user who ran sudo, through that user's config. Details in docs/probe.md.

PRINCIPLES

How it is built, and why

  • Bash stays bash. If POSIX bash and gawk do it well, it stays in bash. Go is for what bash genuinely cannot reach: eBPF, raw tracepoints, a real TUI.
  • One artifact per install. A bundled milog.sh built from modular src/*.sh. You install one file, contributors edit small ones.
  • Cooldown and dedup are not optional. Every rule has a cooldown key, and dedup runs across rules on (ip, path). The day a scanner arrives should not be the day your Discord channel becomes unreadable.
  • Hard gates beat clever heuristics. Anomaly detection has three independent silence gates: minimum days, a per-metric floor, and a non-zero standard deviation. Under-alerting during ramp-up is the better failure.
  • No black boxes. Every fire is written to alerts.log before any destination is tried, and milog alerts reads it back. A delivery that fails goes to send_failures.log, and milog doctor reports the last 24 hours of them.
